## 2\. 界面取证与核心纠错

许多困惑来自一个直觉：把模型选择器里的每一项都当成「同一个 Sol 的推理档位」。这个直觉是错的（`B`）。截图里能看到的固定 Sol 推理选项只有「中」和「高」；「极速 5.5」由另一个模型 GPT-5.5 Instant 提供；「智能」是自动切换策略，不是推理等级；标准产品另有「极高」，但是否显示取决于套餐、工作空间设置与分批发布（`A`）。

### 2.1 截图能直接确认的事实

-   输入框右侧显示「高」、下拉菜单里「高」带勾，说明该对话当时选择了高推理等级（`C`）。
-   主菜单同时列出「智能」「极速 5.5」「中」「高」；截图未出现「极高」（`C`）。
-   主菜单下方存在一个独立的模型子菜单，当前为「GPT-5.6 Sol」，可切换 GPT-5.5、GPT-5.3、o3（`C`）。
-   因此界面至少有两个正交维度：推理 / 速度预设，以及模型 / 旧模型访问。不能把菜单里每一项都解释为同一模型的推理档位（`B`）。

### 2.2 官方映射表

| 界面项 | 官方产品含义 | 执行模型 | 证据 | 说明 |
| --- | --- | --- | --- | --- |
| 智能 | 开启自动切换；复杂请求可从 Instant 切到 Medium | GPT-5.5 Instant 或 GPT-5.6 Sol | `A` `B` | 官方用「自动切换」描述；中文标签「智能」的逐字映射属高可信界面推断 |
| 极速 5.5 | Instant / 即时，面向日常快速回答 | GPT-5.5 Instant | `A` `C` | 截图把模型版本写进标签；官方称 Instant 仍是默认快速模型 |
| 中 | 标准推理 | GPT-5.6 Sol | `A` | 官方明确映射 |
| 高 | 扩展推理 | GPT-5.6 Sol | `A` | 官方明确映射 |
| 极高（截图未显示） | Sol 可提供的最高推理强度 | GPT-5.6 Sol | `A` | Plus 不含；Pro / Business / Enterprise 可用，受工作空间设置与分批发布影响 |
| Pro | 困难任务与长运行工作流 | GPT-5.6 Sol Pro | `A` | 独立 Pro 选项，不等同于 Extra High |

要点：不能从截图缺少「极高」就断定账号一定是 Plus（`B`）。其他可能包括分批发布未覆盖、工作空间管理员关闭、区域 / 客户端差异或界面实验。官方明确说明可用选项还受套餐、工作空间访问设置与逐步发布影响（`A`）。

### 2.3 「三个推理等级」的正确表述

就标准 ChatGPT 产品定义而言，GPT-5.6 Sol 支持 Medium、High、Extra High 三个固定推理预设（`A`）。就这张截图而言，仅能确认 Medium 和 High 两个 Sol 预设可见；Instant 是另一模型 GPT-5.5，智能是自动路由策略。把「智能、极速、中、高」统称为 Sol 的三个或四个推理等级，会把模型选择、路由策略和推理强度三件事混为一谈（`B`）。

### 3.1 模型、强度、模式、路由、基础设施

| 对象 | 定义 | 示例 | 是否改变模型 | 是否改变计算量 |
| --- | --- | --- | --- | --- |
| 模型层级 / 模型 ID | 一组可部署的能力与权重版本标识 | GPT-5.6 Sol、GPT-5.5 Instant、o3 | 是 | 通常是 |
| 推理强度 / effort | 单次请求分配多少推理工作的控制量 | Medium、High、Extra High | 不一定；三者均为 Sol | 是，且按任务自适应 |
| 推理模式 / mode | 标准执行与更重的 Pro 执行 | API 中 standard / pro | 可能仍用同一模型族 | 是；与 effort 独立 |
| 自动路由策略 | 产品按请求特征选择执行路径 | Instant 自动切到 Medium | 可能改变 | 是 |
| 基础设施路由 | 把已确定的请求送到合适区域 / 集群 / 实例 | 按容量、负载、上下文、缓存路由 | 不应改变产品语义 | 目标是降低延迟 / 成本 |

关键：官方费率卡把 Medium、High、Extra High 都归为 GPT-5.6 Sol，并说三者使用不同推理强度（`A`）。这足以支持「同一命名模型层级 + 不同推理预算」的结论（`B`），但不能据此证明每条请求都落到位级一致的权重快照、完全相同的系统提示或相同工具集合——在线产品会滚动更新快照、指令与策略（`B`）。

### 3.2 Extra High 与 Pro 不是同一事物

Extra High 是标准 GPT-5.6 Sol 的最高推理强度；Pro 由 GPT-5.6 Sol Pro 提供（`A`）。API 文档进一步把 `reasoning.mode`（standard / pro）与 `reasoning.effort` 视为相互独立：mode 决定标准还是更重的 Pro 执行，effort 决定该模式内部用多少推理工作（`A`）。因此不能把 Pro 简化成「比 Extra High 再高一档」（`B`）。

### 3.3 Sol / Terra / Luna 与标准 ChatGPT

GPT-5.6 是模型家族，含 Sol、Terra、Luna 三个持久能力层级：Sol 旗舰、Terra 面向能力 / 速度 / 成本平衡、Luna 最快且成本最低（`A`）。标准 ChatGPT 对话只能选 Sol；Terra 与 Luna 在 ChatGPT Work、Codex 和 API 等其他产品面开放（`A`）。API 模型页说明，不带后缀的 `gpt-5.6` 别名路由到 Sol，公开 API 最大上下文 1,050,000 Token、最大输出 128,000 Token，并支持推理 Token（`A`）。这些是 API 能力上限，不应直接当作所有 ChatGPT 套餐表面的实际配额（`B`）。

## 4\. 推理强度的理论基础

要讲清 Medium / High / Extra High 在「原理」层改变了什么，不必假设 GPT-5.6 的未公开架构。可以只用官方对推理模型的公开解释来推。一次回答可以抽象为自回归生成 `p(y | x, e, c)`：`x` 是用户输入与产品注入的上下文，`y` 是生成序列，`e` 是推理强度控制，`c` 是工具、系统指令、安全策略与会话状态等执行条件。这只是行为层抽象，不是对网络结构或参数量的披露（`B`）。

### 4.1 训练时推理与测试时计算

OpenAI 对推理模型的公开解释是：通过强化学习训练模型在作答前进行内部推理，学习细化策略、识别并纠正错误、分解难题、在当前方法失败时尝试替代方法；其早期公开研究显示性能随训练时 RL 计算和测试时思考计算增加而改善（`A`）。GPT-5.6 系统卡也明确称其推理模型经强化学习训练，能在作答前产生较长内部推理，并在训练中学习改进思考过程（`A`）。

### 4.2 软预算，不是硬计时器

API 文档把 `reasoning.effort` 定义为指导模型「思考多少」的参数：较低强度偏向速度和更少 Token，较高强度允许更完整的思考以追求质量；同时模型在每个强度下仍会自适应，简单任务用较少 Token，复杂任务用更多（`A`）。因此合理的形式不是「Medium 固定 5 秒、High 固定 20 秒、Extra High 固定 60 秒」，而是一个条件分布 `N_reason ~ P(N | 难度, effort, 上下文, 采样)`：推理强度改变隐藏推理长度、搜索深度、候选策略数、验证步骤与工具迭代次数的概率分布，但每次采样的实际值并不固定（`B`）。系统卡还指出，即使比较相同「请求推理强度」，实际推理长度也可能随训练阶段变化（`A`）。

### 4.3 为什么更多推理常能提高复杂任务成功率

-   分解深度增加：把多约束问题拆成更多中间子问题。
-   策略搜索空间扩大：更有机会尝试第二、第三种解法，而不是沿首个候选直接输出。
-   内部验证增加：约束检查、单位检查、代码静态检查、事实一致性与工具结果交叉核对。
-   工具规划更完整：更多轮「计划—调用—观察—修正」。
-   长程一致性改善：在复杂报告、代码库或多文件任务中维护全局目标与局部步骤一致。

这些是推理模型的一般行为解释，不意味着所有请求都会执行全部步骤（`B`）。模型内部推理内容不向 ChatGPT 用户展示，API 也只提供可选的推理摘要而不公开原始隐藏推理（`A`）。

### 4.4 更高推理并非单调保证

更高强度提升的是复杂任务上的期望成功概率，而不是确定性正确率（`A`）。常见反例：简单事实问答中额外推理没有收益；错误前提可能被更长地展开；工具源本身错误会被持续传播；随机采样导致同一强度重复运行仍有差异；过度规划可能增加延迟并引入不必要步骤。因此应通过任务集评估收益，而不是按「越高越好」做静态选择（`B`）。

## 5\. Medium / High / Extra High 的实际差异

### 5.1 官方可确认的差异

| 档位 | ChatGPT 官方定义 | 执行模型 | 预期计算特征 | 适用任务 | 主要代价 |
| --- | --- | --- | --- | --- | --- |
| Medium（中） | 标准推理 | GPT-5.6 Sol | 平衡质量 / 可靠性 / 延迟；任务自适应 | 常规研究、复杂写作、数据分析、Agentic coding | 比 Instant 慢；可能产生显著隐藏推理 |
| High（高） | 扩展推理 | GPT-5.6 Sol | 允许更深规划、调试、验证与工具链 | 复杂调试、深度规划、高价值知识工作、长程研究 | 更高延迟与潜在 Token / 工具成本 |
| Extra High（极高） | Sol 的最高推理强度 | GPT-5.6 Sol | 最长的标准 Sol 推理预算区间；仍是自适应软预算 | 安全 / 代码审查、长运行异步工作、最难研究或编码 | 最高延迟；边际收益可能不足；套餐受限 |

### 5.2 不能公开量化的差异

| 问题 | 官方是否披露 | 可靠结论 |
| --- | --- | --- |
| 每档固定隐藏推理 Token 上限？ | 否 | 只能确认随档位与任务复杂度变化，可能从数百到数万 Token；无公开固定阈值（`A` 证实存在，阈值为 `D`） |
| High 是 Medium 的几倍计算量？ | 否 | 不存在可引用的固定倍数；即便平均值存在也随任务分布、快照与服务策略变化（`D`） |
| Extra High 是否对应 API `xhigh`？ | 未明确 | 名称语义相似，但 UI→API 原始枚举映射无官方披露，不能当作已验证事实（`D`） |
| 高档是否总调用更多工具？ | 否 | 高档可能规划更多工具迭代，但仍取决于任务、可用工具、策略与模型判断（`B`） |
| 高档是否用不同参数规模 / 专家数？ | 未披露 | 官方只说同为 GPT-5.6 Sol，不足以证明或否定内部动态专家、推测解码器等（`D`） |
| 每档是否保证固定响应时间？ | 否 | 排队、预填充、推理、工具、解码、安全与网络都会改变总时延（`B`） |

一次网页回答的总时延可拆成 `T_total = T_queue + T_prefill + T_reason + ΣT_tool + T_decode + T_safety + T_network`。提高推理等级主要影响 `T_reason`，并可能间接增加工具轮数与解码前验证；但排队、上下文长度、缓存命中、工具端响应和网络状况同样可能占主导（`B`）。OpenAI 工程文章公开说明其服务栈按区域、容量、加速器类型、集群负载、上下文长度和缓存路由请求，并用负载均衡、KV 缓存、内核优化与推测解码降低成本与时延（`A`）。

### 5.3 按消息同价不代表同计算量

Business / Enterprise 灵活定价费率卡对 Medium、High、Extra High 均按每条消息相同额度计费，并明确三档使用不同推理强度但费率相同（`A`）。这是 ChatGPT 产品的简化计费策略。API 侧则按实际输入、缓存输入和输出 Token 计费，隐藏推理 Token 计入输出 Token（`A`）。因此不能用相同消息费率反推三档实际计算量相同（`B`）——这是两种不同的产品计费抽象。

## 6\. 七层路由与执行链路

所谓「实际原理」不能被压缩成一个路由器或一个 Token 数。一条用户消息至少要穿过七个不同的控制面，每一层职责不同、可观测性不同。下图据 OpenAI 公开资料重构这条链路。

### 6.1 逐层拆解

1.  **用户控制面（`A`）**：用户在输入框选 Instant / Medium / High / Extra High 或启用自动切换，也可能在旧模型菜单选特定模型。工作空间管理员可限制成员可用的模型与选项。这层产生的是产品意图。
2.  **产品语义路由（`A` `B`）**：自动切换开启时，ChatGPT 可根据请求复杂度把 Instant 路径切到 Medium。官方公开的是路由输出与用户可控开关，而不是分类器的输入特征、类型、阈值或规则。可验证的最小模型是二元策略 `r(request, context, policy, quota) ∈ {GPT-5.5 Instant, GPT-5.6 Sol Medium}`。
3.  **模型与推理配置（`A`）**：确定执行模型后施加推理预设。对 Sol，Medium / High / Extra High 控制推理强度；对 Instant，产品目标是快速日常响应。API 暴露更细的 effort 集合，标准 ChatGPT 只暴露产品化子集。
4.  **工具与智能体编排（`A`）**：任务需要搜索、文件、代码执行或计算机使用时，一次消息可能触发多次模型请求与工具调用。OpenAI 把 Codex / ChatGPT Work 的编排描述为连接模型、工具与用户环境的 Rust 编排层，负责延迟发现工具、控制工具输出长度、保持可缓存前缀。
5.  **安全控制面（`A`）**：安全不是仅靠最终文本审核。系统卡公开分层安全栈：模型内安全训练、生成中可中止不安全回答的激活分类器、实时输出阻断，以及跨会话识别不安全模式的自动系统。这些控制可能拒绝、截断、改写或重路由请求，并造成与推理等级无关的额外延迟。
6.  **基础设施路由（`A`）**：模型与策略确定后，请求还要被调度到实际计算资源——全球按地理、容量、加速器类型路由，集群内按负载、上下文长度、缓存分配实例，实例内还要在加速器与计算核心间划分工作。这影响吞吐、时延、缓存命中和成本，但原则上不改变用户选择的产品语义。
7.  **配额回退（`A`）**：配额逻辑与复杂度路由不同。官方帮助中心说明，手动选 Medium / High / Extra High 使用 GPT-5.6 Sol；达到 GPT-5.6 推理限额后，ChatGPT 可能继续使用 GPT-5.4 Thinking mini。因此连续会话里的模型身份可能随额度状态变化。

### 6.2 可解释的最小路由模型

从公开材料可建立一个不超出证据的最小决策模型（`B`）。它不排除系统内部有更复杂的特征工程、分类器与实验分流；只是公开资料不支持更细的断言：

```text
if user_selected in {"Medium", "High", "Extra High"}:
    execute(model="GPT-5.6 Sol", effort_preset=user_selected)
elif user_selected == "Instant" and auto_switch_enabled:
    if product_complexity_policy(request, context, tools, account_state):
        execute(model="GPT-5.6 Sol", effort_preset="Medium")
    else:
        execute(model="GPT-5.5 Instant")
else:
    execute(model="GPT-5.5 Instant")
```

_清单 1 · 公开证据允许的最小产品路由伪代码。这不是 OpenAI 源代码。_

伪代码之后，系统还会独立施加：安全控制、工具编排、基础设施路由与配额回退——它们不改变上面这段路由决策，但会进一步影响可见行为与时延（`B`）。

## 7\. 自动「智能」路由的已知边界

### 7.1 已验证事实

-   Instant 仍是默认快速模型，由 GPT-5.5 Instant 提供（`A`）。
-   符合条件的付费方案可让 ChatGPT 对复杂请求自动使用更多推理，界面表现为从 Instant 切到 Medium（`A`）。
-   用户可在模型选择器配置中开关自动切换（`A`）。
-   自动切换后的消息使用 GPT-5.6 Sol 并按 Sol 消息额度计费；自动切换不计入手动选择推理的使用额度（`A`）。

### 7.2 未验证的常见推断

| 常见说法 | 判定 | 原因 |
| --- | --- | --- |
| 「智能会在 Instant / Medium / High / Extra High 中动态选择」 | 未获官方支持 | 当前官方只明确 Instant → Medium（`D`） |
| 「智能路由只看提示词长度」 | 无证据 | 可能用复杂度、上下文、工具需求、策略与实验特征；具体未公开（`D`） |
| 「选高之后系统仍会自动降到中」 | 未公开 | 除配额回退、安全或服务故障外，官方没有公开手动 High 被语义降档的规则（`D`） |
| 「路由器就是另一个小模型」 | 未公开 | 可能是分类模型、规则、混合策略或多级系统，官方未披露（`D`） |
| 「智能比手动中更强，因为它会判断难度」 | 不成立 | 路由到 Medium 时产品定义仍是 Sol 标准推理；是否更优取决于任务与路由准确率（`B`） |

路由误差有真实的产品后果（`B`）：欠路由让复杂任务仍由 Instant 处理，表现为推理不足、约束遗漏；过路由让简单任务切到 Medium，增益有限但延迟上升并消耗 Sol 额度；长会话、附件、工具可用性或工作空间策略改变路由环境，使同一表面提示得到不同执行路径。网页用户通常只看得到产品标签或切换提示，读不到隐藏 `reasoning_tokens`，难以区分「推理不足」与「工具 / 数据源失败」。

## 8\. 隐藏推理 Token、上下文与延迟

隐藏推理 Token 是理解「同价不同计算量」的关键。它不向用户展示，但在 API 中占用上下文并按输出 Token 计量，且按任务难度自适应——不是固定计时器或固定上限。

![隐藏推理 Token 的两个视角：左侧是一个上下文窗口里输入、隐藏推理、工具返回、可见输出各占一段；右侧是中、高、极高三档对应的推理 Token 概率分布，越高越往右且越宽](/content-assets/tech-series/tech-series-gpt-5-6-sol-的推理等级与路由机制-官方能证明什么-什么仍不可知/d3c6d0c478.svg)

_图 3 · 隐藏推理 Token 与自适应软预算。左：一个上下文窗口装的不只是聊天文字；右：每档是一个概率分布而非固定值。比例仅为示意，非 GPT-5.6 实测数据。_

### 8.1 三类输出相关 Token

| 类型 | 是否对用户可见 | 是否占上下文 | API 计量 | 作用 |
| --- | --- | --- | --- | --- |
| 输入 Token | 可见原始输入；系统 / 工具定义可能不可见 | 是 | `input_tokens` | 承载提示、历史、系统指令、工具定义与附件 |
| 隐藏推理 Token | 不展示原文 | 是 | `output_tokens_details.reasoning_tokens`；按输出 Token 计费 | 分解问题、比较方案、内部验证、计划工具调用 |
| 可见输出 Token | 可见 | 是 | `output_tokens` 的一部分 | 最终答案、工具调用参数、可选推理摘要 |

### 8.2 上下文窗口不是只装聊天文字

API 文档明确说明隐藏推理 Token 仍占用上下文窗口，复杂任务可生成数百到数万推理 Token（`A`）。在 ChatGPT 产品中，还可能有系统指令、记忆、项目上下文、附件解析、工具定义与返回、网页内容、安全元数据和格式开销（`B`）。长上下文任务即使可见输出不长，也可能因隐藏推理与工具结果消耗大量上下文。此外，API 里的 `max_output_tokens` 限制的是生成总量（含隐藏推理）；若预算在推理阶段耗尽，响应可能以 incomplete 结束、甚至没有可见文本（`A`）。这说明「允许更多推理」与「保证更长最终答案」是两个不同目标。

### 8.3 时延观测的正确指标

| 指标 | 定义 | 能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| TTFT | 发送到首个可见 Token 的时间 | 排队、预填充、初始推理与工具前置开销 | 不能单独估计总推理 Token |
| 总完成时延 | 发送到最终完成的时间 | 用户实际等待成本 | 受网络和工具影响，不能直接归因 effort |
| 可见输出速率 | 可见 Token / 解码时间 | 解码吞吐与流式体验 | 隐藏推理期间没有可见 Token |
| `reasoning_tokens`（API） | 隐藏推理 Token 数 | 最接近推理计算分配的公开代理量 | 不等价于 FLOPs，也不能读取推理内容 |
| 工具调用数 / 轮数 | 一次任务的工具迭代数量 | Agentic 深度与外部依赖 | 更多调用不一定更好，可能是低效或失败重试 |

## 9\. 安全控制与配额回退

### 9.1 安全控制会改变可见行为

GPT-5.6 系统卡披露的安全栈包括：训练进模型的安全行为、生成中激活分类器、实时输出扫描与阻断、跨会话模式检测，以及账号级执法（`A`）。对高风险网络安全或生物请求，较强模型可能触发更保守的检查。用户可能看到拒绝、响应被中止、要求额外验证或建议改用较低能力模型。同一提示可能出现不同阻断结果，原因包括：隐藏会话上下文不同、模型采样不同、安全策略持续更新、以及推理等级不同（更强推理可能生成更具体的潜在高风险步骤而触发更严格干预）——这不是「高档更少拒绝」或「高档更多拒绝」的单调关系（`B`）。

### 9.2 配额回退与套餐权限

达到 Sol 推理限额后可能回退 GPT-5.4 Thinking mini（`A`）。若实验没记录额度状态，会把模型切换误判为推理强度差异。严格测试应在每组实验前确认额度、在新对话运行、随机化顺序，并保存界面模型标签与任何回退通知。可用性还受套餐与工作空间权限约束：

| 方案 | Medium / High | Extra High | Sol Pro | 备注 |
| --- | --- | --- | --- | --- |
| Plus | 包含 | 不包含 | 不包含 | 标准 ChatGPT；截图只出现中 / 高与此一致，但不能据此唯一判定套餐 |
| Pro | 包含 | 包含 | 包含 | 可用更高强度与 Pro |
| Business | 包含 | 包含 | 包含 | 还受管理员工作空间访问设置影响 |
| Enterprise | 包含 | 包含 | 包含 | 还受管理员、数据驻留与组织策略影响 |
| Free / Go | 不含 Sol | 不包含 | 不包含 | Go 的「思考」不使用 GPT-5.6 Sol |

## 10\. ChatGPT UI 与 API 的关系及不可等同项

### 10.1 API 暴露的 effort 更细

OpenAI 通用推理指南列出可由不同模型支持的 `none`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max` 等取值，并要求以具体模型页为准（`A`）。GPT-5.6 Sol 的 API 支持推理 Token，模型目录显示其支持多个推理强度（`A`）。标准 ChatGPT 则把这些复杂控制压缩成 Instant、Medium、High、Extra High 和 Pro 等产品标签（`A` `C`）。

### 10.2 不能直接建立的映射

| ChatGPT 标签 | 可以确认 | 不能确认 |
| --- | --- | --- |
| Medium | 使用 GPT-5.6 Sol 标准推理（`A`） | 是否逐字传递 `reasoning.effort="medium"`；是否叠加产品专用预算 / 系统提示 / 工具策略（`D`） |
| High | 使用 GPT-5.6 Sol 扩展推理（`A`） | 是否对应 API `high` / `xhigh` 或内部预设；固定 Token / 时间预算（`D`） |
| Extra High | Sol 的最高推理强度（`A`） | 是否等于 API `xhigh` 或 `max`；是否按套餐再做动态上限（`D`） |
| Pro | 由 GPT-5.6 Sol Pro 提供（`A`） | 是否直接等于 API `reasoning.mode="pro"`；产品端是否用独立模型 ID 或其他实现（`D`） |
| 智能 / Smart | 可能从 Instant 自动切到 Medium（`A` `B`） | 路由分类器结构、输入特征、阈值、灰度实验中是否有更多路径（`D`） |

API 模型页公布 GPT-5.6 Sol 最大上下文 1,050,000 Token、最大输出 128,000 Token（`A`）。这是 API 端能力上限；ChatGPT 产品可能对不同套餐、标准聊天、Work、Codex、附件和工具工作流设置更低或不同的有效上限，并需为隐藏系统上下文和推理 Token 预留空间（`B`）。API 别名 `gpt-5.6` 可随官方更新指向新快照；需要严格可复现时，应记录日期、API 返回的模型字段、SDK 版本和全部请求参数（`A`）。

## 11\. 验证方案与本报告的验证结果

### 11.1 验证目标分层

| 目标 | 可用方法 | 可观测量 | 能否验证内部机制 |
| --- | --- | --- | --- |
| 确认界面选项与模型标签 | 网页截图、官方帮助中心、发布说明 | 菜单文本、选中项、切换提示 | 能验证产品映射，不能验证服务端参数 |
| 比较三档答案质量 | 同一任务集的随机化重复实验 | 任务成功率、约束满足、事实 / 代码正确性 | 能比较黑盒行为，不能读取隐藏推理 |
| 比较延迟 | 浏览器时间戳 / HAR + API 计时 | TTFT、总时延、P50 / P95 | 只能归因到完整链路，不能单独归因模型计算 |
| 测量隐藏推理 Token | Responses API usage 对象 | `reasoning_tokens` | 可测 API 请求，不证明网页 UI 映射 |
| 验证自动路由 | 开启智能，构造难度梯度并观察切换标签 / 计费 | Instant 或 Medium 路径、切换提示 | 可估计路由边界，不能恢复分类器 |
| 验证配额回退 | 在合法使用范围内观察额度耗尽后的提示 | 模型标签、重置时间、回退行为 | 可验证产品行为，不应故意滥用或绕过限制 |

网页黑盒实验要点：建立覆盖短事实、逻辑、数学、复杂约束写作、代码调试、长文档综合、网络研究与工具任务的任务集；固定输入并在新对话运行；对 Medium / High / Extra High 用拉丁方或随机顺序；每个任务 / 档位至少重复 5 次；记录套餐、额度、模型标签与任何回退 / 安全提示；盲评质量并报告成对 bootstrap 置信区间。网页实验测不到的量包括：原始隐藏推理文本与精确 FLOPs、内部快照 / 参数 / 专家激活、自动路由分类器特征与阈值、UI 标签到服务端 `reasoning.effort` 的精确映射（`D`）。

### 11.2 API 控制实验的最小形态

API 实验的价值在于同一模型、同一提示下显式设置 `reasoning.effort`，并从 usage 对象读取 `reasoning_tokens`；建议先比较 medium、high、xhigh。它描述的是 API effort 曲线，不能自动证明 ChatGPT 网页 Medium / High / Extra High 使用相同枚举（`B`）。一个最小骨架足以说明思路（完整实验应加入随机化、重复采样与盲评）：

```python
from openai import OpenAI
client = OpenAI()
for effort in ["medium", "high", "xhigh"]:
    r = client.responses.create(
        model="gpt-5.6",
        input=[{"role": "user", "content": PROMPT}],
        reasoning={"effort": effort},
        max_output_tokens=32000,
    )
    print(effort, r.model, r.usage.output_tokens_details.reasoning_tokens)
```

_清单 2 · 读取 `reasoning_tokens` 的最小 Responses API 探针。运行会产生 API 费用；`max_output_tokens` 过低会在推理阶段截断，高档受影响更大。_

综合来看，公开证据已能验证：产品映射、自动切换方向、三档同属 Sol、隐藏推理 Token 的存在与自适应、配额回退、安全层与基础设施路由。公开资料不足以验证：每档固定预算、UI→API 精确枚举、模型参数 / MoE 拓扑和自动路由算法。为避免伪精确，本报告不提供未经实测的倍数、秒数或 Token 阈值。

## 12\. 选型建议、故障模式与结论

### 12.1 实际选型矩阵

| 任务条件 | 推荐入口 | 原因 | 升级 / 降级条件 |
| --- | --- | --- | --- |
| 日常问答、改写、短摘要、低风险格式化 | Instant 或 智能 | 低延迟，复杂时可自动切到 Medium | 若约束遗漏或出现多步依赖，手动 Medium |
| 明确多步推理、研究、数据分析、常规代码 | Medium | 官方定位的质量 / 延迟平衡点 | 若端到端失败或调试深度不够，升级 High |
| 复杂调试、架构设计、长程规划、高价值知识工作 | High | 允许扩展推理与更完整工具计划 | 若长运行、极高风险审查或多次失败，评估 Extra High |
| 深度研究、安全 / 代码审查、异步长任务 | Extra High | 标准 Sol 的最高推理强度 | 仅在评估证明收益超过时延成本时使用 |
| 最难且可容忍更高计算的任务 | Sol Pro / Pro | 更重的执行路径，独立于普通三档 | 不要把 Pro 当作 Extra High 的同义词 |

### 12.2 常见故障模式与诊断

| 症状 | 可能原因 | 诊断动作 | 处理 |
| --- | --- | --- | --- |
| High 仍快且答案很短 | 任务简单，自适应少推理；缓存 / 容量良好 | 换可验证复杂任务，不以回答长度推断推理量 | 保持 High 或降 Medium，按质量判断 |
| High 比 Medium 慢但质量不升 | 任务已达天花板；工具 / 数据源限制 | 查错误类型、工具结果与多次重复统计 | 降 Medium，改进提示与数据源 |
| 同一提示结果波动大 | 随机采样、系统负载、路由 / 工具状态变化 | 新对话重复，记录时间与产品状态 | 用统计分布而非单次结果 |
| 突然能力下降 | 额度回退、旧模型、工作空间策略或安全干预 | 查模型标签、额度通知、管理员设置 | 等待重置或明确选择可用模型 |
| 长任务中途无可见输出 | 隐藏推理或工具阶段较长；API 输出预算耗尽 | 记录 TTFT / 工具阶段；API 检查 incomplete | 提高合理输出预算或拆分任务 |
| 引用错误或搜索不足 | 数据源 / 搜索策略 / 工具失败，而非纯推理预算 | 核查来源、重跑工具、要求逐条证据 | 改进检索约束，必要时 High / Extra High |

### 12.3 最终结论

GPT-5.6 Sol 的 Medium、High、Extra High 本质上是同一命名模型层级上的不同推理强度预设。它们改变模型在一次请求中用于内部推理、计划、验证和工具迭代的计算分配，但该分配是任务自适应的软预算，不是公开固定时长或固定 Token 配额（`A` `B`）。截图中的「智能」应理解为产品路由开关，其已公开行为是让 GPT-5.5 Instant 在复杂请求上自动切到 GPT-5.6 Sol Medium；「极速 5.5」是另一个模型；「中」「高」才是截图中可见的 Sol 推理等级；「极高」是标准产品支持的第三个 Sol 档位，但截图未显示的原因无法仅凭截图确定（`A` `C`）。

所谓「实际原理」不能被压缩成一个路由器或一个 Token 数：完整链路同时包含产品语义路由、模型与 effort 配置、隐藏推理 Token、工具 / 智能体循环、安全控制、基础设施路由与配额回退。官方公开资料已足以确定这些层的存在与基本职责，但不足以公开 GPT-5.6 的参数规模、神经网络拓扑、每档预算、UI 到 API 枚举映射和分类器实现。对这些内部细节应保持明确的不可知边界（`D`）。

## 13\. 与本系列的连接

-   **对照《前沿模型参数量估算》**（`/frontier-model-parameter-estimates`）：那篇文章尝试为前沿模型的参数量给出区间估算，而 GPT-5.6 Sol 的参数量、层数、注意力结构、是否 MoE / 专家数在官方模型页和系统卡里都**明确未披露**（`D`）。两篇放在一起正好构成对照：能估算的用方法去逼近，不能确知的就老实标为未知——这正是本文 A/B/C/D 纪律的意义。
-   **对照《Pi Agent Runtime》**（`/pi-agent-runtime`）：Pi 把「模型抽象 / agent-loop / harness / 产品层」分成清晰的四层。本文的七层路由链路是同一种工程直觉在服务侧的展开——用户意图、语义路由、模型 + effort、工具编排、安全、基础设施、配额回退各司其职。理解「一条消息要穿过多层控制面」，能帮你把「为什么 High 更慢」「为什么同一提示结果不同」这类现象拆到正确的层上，而不是笼统归因给「模型变笨了」。
